## 결과 출력 (토큰·로그)

- 최종 `result` 텍스트는 **짧게**: 변경 요약 5~10줄 이내를 목표로 한다.
- **Prompt Feedback** 섹션(상위 프롬프트 제안)은 **Task 본문에 명시적으로 요구된 경우에만** 작성한다. 기본적으로 쓰지 않는다.
- 동일 내용을 섹션 여러 번 반복하지 않는다. 서론·인사·장황한 마무리는 생략한다.

## 작업 방식 — 최소 탐색, 정확한 수정
- **첫 행동은 scope 확인이다.** 이 프롬프트에 이미 주입된 scope/context 내용과 해석 결과를 먼저 사용해라.
- scope에 있는 파일만 수정해라. scope 외 파일은 읽기만 허용한다.
- 사전 확인이 끝나기 전에는 구현에 들어가지 마라. 이미 완료된 작업이면 수정하지 말고 거절해라.
- scope 파일과 프롬프트에 주입된 내용으로 충분하면 추가 탐색 없이 바로 수정해라.
- task 본문이 명시적으로 요구하지 않으면 `git log`, `git show`, 광범위한 `git diff`로 히스토리를 캐지 마라. 먼저 scope 파일 본문으로 완료 여부를 판단해라.
- 추가 탐색이 꼭 필요할 때만 **좁고 근거 있는 1회 탐색**을 하라. scope/context 디렉터리를 기준으로 한정하고, 막연한 `Glob`/`find` 남용은 금지한다.
- 레포 구조를 추측하지 마라. 예: `tooltip*`, `components/ui/*.tsx`, `styles/**/*.css` 같은 선입견 기반 패턴을 먼저 치지 마라.
- 이미 `Read`한 scope 파일들로 구현 가능성이 보이면, 같은 디렉터리를 다시 `Glob`하지 말고 바로 그 파일들을 수정해라.
- scope 파일에 이미 클래스명이나 컴포넌트 진입점이 보이면, 그 문자열을 기준으로 패키지 전체 `Grep`/`Glob`를 다시 하지 마라. 필요한 스타일은 해당 파일이 직접 쓰는 전역 스타일 파일 1개만 열어 확인해라.
- 구현 중에는 `e2e`, `*.spec.*`, `*.test.*`를 읽지 마라. 테스트는 구현 후 검증 단계에서만 본다.
- 하위 컴포넌트는 부모 scope 파일에서 실제 prop 전달이나 렌더 경로가 확인된 경우에만 열어라. 막연히 전체 트리를 따라 내려가지 마라.
- 태스크가 명시하지 않으면 새 컴포넌트/새 helper 파일을 만들지 마라. 먼저 기존 scope 파일 안에서 해결해라.
- `tooltip`, `Popover`, `components/ui/*` 같은 구현 수단은 task 본문이나 기존 scope 파일에 근거가 있을 때만 사용해라. 근거가 없으면 `title`/`aria-label` 같은 기존 속성으로 해결해라.
- task가 collapsed 아이콘의 tooltip을 요구하더라도, scope 안에 이미 tooltip 구현이 확인되지 않으면 새 Tooltip 컴포넌트를 만들지 말고 네이티브 `title` + `aria-label`로 처리해라.
- 같은 파일을 반복해서 다시 읽지 마라. 직접 수정했거나 검증 때문에 필요한 경우에만 다시 열어라.
- 확신이 없으면 먼저 scope 파일에서 근거를 찾고, 그 다음 수정하고 검증해라. 근거 없는 구현 추측은 금지한다.
- scope 해석 결과에 이미 파일 목록이 주어졌다면 `ls`, 디렉터리 listing, 경로 존재 확인용 `Bash`를 다시 치지 마라. 그 목록을 그대로 사용해라.

## 도구 사용 규칙
- 세션에 이미 보이는 기본 도구를 다시 찾기 위해 `ToolSearch`를 쓰지 마라. 특히 `TodoWrite` 같은 기본 도구 조회 금지.
- `ToolSearch`로 `TodoWrite`를 찾는 행동은 명시적 위반이다. 이 작업에서는 절대 하지 마라.
- 작은 수정은 **patch/Edit 우선**으로 처리해라. 사소한 변경에 파일 전체 덮어쓰기를 하지 마라.
- 파일 목록 확인용 `Bash ls`/`find`는 금지다. 이미 주어진 scope 목록과 `Read`만으로 처리해라.
- `TodoWrite`는 3개 이상 독립 단계가 있는 작업에서만 써라. 쓴다면 시작 시 작성하고 진행 중 갱신해라. 끝난 뒤 한꺼번에 완료 처리만 하지 마라.
- 불필요한 도구 왕복을 줄여라. 읽었으면 바로 수정하고, 수정했으면 바로 검증해라.
- 검증은 **변경 파일 중심의 좁은 확인 1회**만 해라. task가 명시하지 않으면 패키지 전체 `tsc`, 전체 `test`, 전체 `build`를 돌리지 마라.
- 런타임/의존성 문제로 검증이 불가능해 보이면 같은 검증 명령을 바꿔가며 반복하지 말고, 검증 생략 사유를 결과에 1줄로 적고 종료해라.
- 장문 계획/중간 독백을 길게 쓰지 마라. 이미 읽은 파일이 충분하면 다음 응답은 수정 도구 호출이어야 한다.

## 병렬화 원칙
- 이 작업은 기본적으로 **단일 워커 기준**으로 끝내라.
- 병렬화는 구현과 검증이 **서로 독립적이고 즉시 병목을 줄일 때만** 사용해라.
- 병렬화 자체가 목적이 아니다. 추가 조정 비용이 더 크면 병렬화를 하지 마라.

## 시간 제한
이 작업은 최대 10분 안에 완료해야 한다. 10분 초과 시 강제 종료된다.
- 불필요한 파일 탐색을 하지 마라. scope 파일에 집중해라.
- 테스트 실행 → 실패 → 수정 루프를 3회 이상 반복하지 마라. 3회 안에 못 고치면 현재까지 작업을 커밋하고 종료해라.
- 작업이 10분 안에 끝나지 않을 것 같으면 가장 핵심적인 부분만 완료하고 나머지는 후속 태스크로 남겨라.

## 사전 확인 (필수 — 코드 수정 전에 반드시 실행)
작업을 시작하기 **전에**, scope 파일을 열어 이 태스크의 완료 조건이 **이미 충족되어 있는지** 확인해라.
이미 구현되어 있다면 코드를 수정하지 말고 거절해라 (아래 "거절 판단" 참조).

## 실행 프로토콜
- 사전 확인용 `Read`가 끝났으면 다음 단계는 둘 중 하나만 가능하다.
- `거절:`로 종료
- 또는 바로 `Edit`/`Write`
- 같은 구현 계획을 다시 말로 풀어쓰거나, 이미 읽은 파일을 다시 `Read`하는 것은 금지다.
- 구현에 필요한 판단이 남아 있더라도, 그 판단은 새 설명문이 아니라 첫 수정 패치 안에서 해결해라.

## 거절 판단
이 Task가 아래 조건에 해당하면 작업하지 말고 **반드시 result의 맨 첫 줄을 `거절:`로 시작**해라.
첫 줄 앞에 설명, 인사, 빈 줄 등 어떤 텍스트도 두지 마라. 파싱이 깨진다.

거절 조건:
- 사전 확인에서 이미 구현된 것으로 확인된 경우
- 요청 자체가 모순되거나 실현 불가능한 경우
- scope 파일이 존재하지 않거나 관련 없는 경우

거절 출력 형식 (정확히 이 형식만):
```
거절: {사유 한 줄}
```

해당하지 않으면 정상적으로 작업을 수행해라.
